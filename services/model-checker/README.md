# Проверка исходного ZIP через AGR Checker 1.6.1

Состояние на 03.10.2026: API и worker развёрнуты на существующей VM
`viewer-voice-01`, очередь PostgreSQL — на `viewer-backend-01`. Viewer 0.97.3
включает кнопку через `https://voice-api.agr.vision/model-check`. Это выпуск
GitHub Pages; Caddy-выпуск `agr.vision` остаётся 0.96.
См. [эксплуатацию на общей VM](deploy/README.md).

## Поток проверки

1. Viewer предлагает загруженные и синхронизированные ZIP НПМ/ВПМ текущей
   комнаты. Локальные несохранённые файлы, Env и отдельные FBX/GLB исключены.
2. API получает `model_id` и пользовательский Bearer JWT. URL файла, имя роли,
   путь Storage, параметры Blender и версию Checker клиент не задаёт.
3. PostgreSQL проверяет владельца проекта, выбирает включённый обработчик и
   фиксирует версию исходника. Повторный запрос того же ZIP и обработчика
   возвращает существующее задание; максимум четыре активных задания на проект.
4. Worker получает задание с lease через `FOR UPDATE SKIP LOCKED`, скачивает
   оригинальные байты из фиксированного Supabase Storage и считает SHA-256.
5. Проверенный снимок host-wrapper запускает закреплённый Docker image ID.
   Внутри контейнера выполняются проверка ZIP, AGR Checker 1.6.1 и отдельно
   обозначенные дополнительные проверки GeoJSON. Env исключается до Blender.
6. Worker сохраняет отчёт только при совпадении SHA-256, image ID, хеша wrapper,
   версии Checker и нормативной редакции. Viewer показывает этапы и все
   состояния пунктов: ошибки, рекомендации, пройдено, не проверено.

Проверяются исходные файлы. Изменения материалов, геометрии и координат для
отображения во Viewer в проверку не попадают. `completed` означает завершение
обработки, а не соответствие всем требованиям и не официальную приёмку.

## Состав

- `api.mjs` — HTTP API на Node.js 22+, только встроенные модули. Использует
  публичный anon key и JWT пользователя; service-role ключ ему не нужен.
- `worker.mjs` — один последовательный worker на Node.js 22+, Python 3 и Docker.
- `supabase/migrations/20261003000100_model_check_jobs.sql` — отдельная
  транзакционная миграция: задания, реестр обработчиков, lease и RPC с RLS.
- `scripts/modules/ui/model-check-panel.js` — окно отчёта, опрос только открытого
  окна, отмена, JSON-экспорт, прекращение запросов при смене комнаты/dispose.
- Приватный комплект Blender находится вне публичного репозитория:
  `LPMVIEW/knowledge/moscow-models/experiments/agr-checker-1.6.1/`.
  Сборка — `linux/prepare-build.py` и `linux/Dockerfile`, запуск контейнера —
  `linux/run-fixture.py`. На общей VM используется `container-runner.py` из этого
каталога, который отказывается работать с rootful Docker. В GitHub Pages исходники моделей/проверяющего архива
  и приватная база знаний не копируются.

## Права и актуальность

Владелец проекта и superuser запускают/отменяют задания. Участник приглашённой
комнаты читает отчёты только её моделей. Отзыв членства сразу закрывает доступ
через RLS. Удаление проекта/модели удаляет связанные задания и отчёты.
Прямые INSERT/UPDATE/DELETE заданий клиенту запрещены. Таблицы engine/lease и
RPC worker доступны только `service_role`; lease token не входит в отчёт.

`source_revision` — MD5 от версии метаданных модели и Storage object
(`version`, `updated_at`, metadata и ID). Это **маркер версии, не хеш ZIP**.
SHA-256 считается по реально скачанным байтам и проверяется контейнером.
Storage используется только через API; SQL читает его метаданные, не изменяет
таблицы Storage. Обычная замена объекта или смена пути аннулирует результат для
текущей модели. Проверка версии повторяется в heartbeat, при завершении и при
чтении отчёта. Старый отчёт остаётся доступным как исторический, с предупреждением. Отдельный
признак `engine_current` указывает, относится ли отчёт к включённой версии
обработчика. В окне также показана дата завершения.

Lease действует 30 секунд, heartbeat отправляется каждые 4 секунды. Host-wrapper
останавливает контейнер, если локальная отметка heartbeat старше 10 секунд.
Потеря lease, отмена, timeout и ошибка обработки не становятся успешным отчётом.
Истёкшие задания переводятся в `incomplete` при следующем запросе worker к
очереди. Если остановлены все worker, состояние обновится после их восстановления.

Документация основы протокола: [PostgREST JWT и роли](https://docs.postgrest.org/en/v13/references/auth.html),
[Storage schema — только чтение](https://supabase.com/docs/guides/storage/schema/design),
[PostgreSQL SKIP LOCKED](https://www.postgresql.org/docs/17/sql-select.html).

## Развёртывание после испытаний на отдельном стенде

API и worker запускаются отдельно. Rootful Docker требует выделенного хоста:
доступ к его daemon является административной привилегией. На выбранной владельцем
общей VM используется **отдельный rootless Docker**, обязательные cgroup v2/systemd
и лимиты ресурсов; доступ к системному Docker worker не получает.
Рабочий service-role ключ передавать только worker через закрытый environment
file, не в браузер, репозиторий, командную строку или контейнер Blender.

1. Сделать резервную копию БД и применить **только новую миграцию**. Полный
   `supabase/schema.sql` предназначен для тестов/новой базы, не для production.
   После миграции обновить schema cache PostgREST (`NOTIFY pgrst, 'reload schema'`).
2. Подготовить приватный образ и host-wrapper. Проверить SHA-256 оригинального
   `SintezAGRChecker_v1.6.1.zip`:
   `f935b5079bdd5f2fdde9bf1fac1250483bf05112b0a49ecc947a4a80da77fa8d`.
   Зарегистрировать **новый** `model_check_engines.revision` с фактическими
   `image_id` (`sha256:…`) и `wrapper_sha256`. Идентичность существующей записи
   менять запрещено триггером. При смене адаптера/образа нужна новая revision.
3. Настроить и запустить API/worker, проверить реальный ZIP на целевом Linux.
   После этого включить ровно одну запись engine. Пока реестр пуст или все
   записи выключены, API отвечает 503 и не создаёт задания.
4. Разрешить HTTPS API только нужным origins и настроить reverse proxy с
   ограничением размера HTTP body и числа запросов. API по умолчанию слушает
   `127.0.0.1:8081`. Если используется префикс URL, proxy должен снимать его.
5. Указать HTTPS URL сервиса в `modelCheckApiUrl` конфигурации конкретного
   выпуска Viewer. Продвижение `agr.vision` — отдельная операция по
   `docs/viewer-releases.md`; push в `gh-pages` этого не делает.

API:

```text
SUPABASE_URL=https://supabase.example
SUPABASE_ANON_KEY=<public anon key>
MODEL_CHECK_ALLOWED_ORIGINS=https://viewer.example
HOST=127.0.0.1
PORT=8081
node services/model-checker/api.mjs
```

Worker:

```text
SUPABASE_URL=https://supabase.example
SUPABASE_SERVICE_ROLE_KEY=<secret from protected environment file>
MODEL_CHECK_ENGINE_REVISION=<registered immutable revision>
MODEL_CHECK_WRAPPER=/opt/lpmview/checker/linux/run-fixture.py
MODEL_CHECK_WORK_DIR=/var/lib/lpmview-checker/jobs
MODEL_CHECK_PYTHON=/usr/bin/python3
node services/model-checker/worker.mjs
```

Wrapper и исходный код сервиса должны быть недоступны для записи пользователю
Blender. Work directory принадлежит worker, mode 0700. Не хранить там готовые
отчёты вручную: отдельная папка задания удаляется в `finally`. В базе остаётся
нормализованный отчёт, а не stdout Blender. На ошибке публикуется безопасный код,
без путей сервера и содержимого служебных ключей.

Маршруты API:

| Метод | Путь | Результат |
|---|---|---|
| POST | `/jobs` | `{ "model_id": "uuid" }` → `{ job }` |
| GET | `/models/:modelId/jobs` | Последние 20 заданий без тела отчёта |
| GET | `/jobs/:jobId` | Состояние, `source_current`, `engine_current` |
| GET | `/jobs/:jobId/report` | Завершённый отчёт; 409 до готовности |
| POST | `/jobs/:jobId/cancel` | `{}` → запрос отмены |

## Ресурсные ограничения и оставшиеся границы

Развёрнутый `container-runner.py`: контейнер `linux/amd64`, network none, read-only
root/input, отдельный writable output, cap-drop ALL, no-new-privileges, 128 PID,
**2 CPU, 4 GiB памяти без swap и 2 GiB tmpfs**. Весь пользователь Checker ограничен
2,5 CPU / 5 GiB; временная файловая система — 16 GiB.
Приватный локальный runner для сравнительных испытаний сохраняет 4 CPU / 6 GiB. ZIP ограничен 2 GiB, отчёт — 4 MiB;
перед запуском worker требует 8 GiB свободного диска. Обработка ограничена
600 секундами, внешний deadline включает ещё 60 секунд для загрузки/очистки.
Это ограничения сервиса, **не нормативные лимиты моделей Москвы**. Архив,
которому не хватает ресурсов, получает незавершённую проверку.

Сейчас принимается расширение `.zip` в нижнем регистре: исходный файл не
переименовывается для обхода поведения стороннего Checker. Неоднозначности
требований и ручные пункты остаются отдельными; IFC не проверяется.

Текущий образ включает наш адаптер кеширования UV-индексов: он ускоряет
доступ к данным Blender, не заменяя формулы Checker. Совпадение отчётов со
штатным оператором проверено на контрольных НПМ и ВПМ. Для большого Ground
полная сверка с неоптимизированным прогоном не завершена: тот достиг лимита
7200 секунд. Это остаётся границей верификации адаптера. Исходный манифест
Checker 1.6.1 заявляет Windows x64; Linux-контейнер является нашей испытанной
адаптацией, а не заявленной автором Linux-поставкой.

На целевой Linux VM контрольный НПМ прошёл за 5,864 с с тем же отчётом, что
локальный эталон. Проверены реальные Storage/version metadata комнаты APEX.
API ограничивает запросы и конкуренцию; systemd контролирует worker/диск, при
старте worker удаляет остатки своих контейнеров и временных заданий.
Отчёты сохраняются до удаления исходной модели; автоматического удаления
истории по возрасту нет. Длительная нагрузка, одновременная голосовая конференция
и физический iPad остаются отдельными границами верификации.

## Проверки

`npm run ci:verify` включает Node-тесты API/worker, окно отчёта в Chromium,
связку окна с настоящим lifecycle Viewer и существующие проверки импорта,
рендера, комнат и очистки. PostgreSQL/RLS тесты выполняются отдельным GitHub
workflow `Database Permissions` на PostgreSQL 17.

Дополнительно выполнены локальные прогоны настоящих ZIP через Blender:
НПМ — 39 passed / 2 failed / 3 warning / 28 not_checked;
ВПМ — 63 / 2 / 2 / 53; Env — `not_applicable`.
Проверена конкуренция: 16 запросов одного исходника дали одно задание;
3 параллельных worker получили 2 разных задания и один пустой ответ.

Полная локальная интеграция дополнительно испытана через PostgREST 13.0.0:
подпись тестового JWT проверяется самим PostgREST, права — настоящим PostgreSQL
17, оригинальный НПМ ZIP обрабатывается настоящим Blender, отчёт записывается
в БД и читается приглашённым гостем. В этом стенде Storage download заменён
локальным HTTP-потоком; production Supabase Storage и его токены не использовались.
Отмена на Ground ZIP 239,5 МБ завершилась за 4,11 с от старта задания;
успешный отчёт не записан, рабочая папка удалена. Это одна диагностическая проба,
не SLA времени отмены на сервере.
